네 발표 시작하겠습니다. 저는 이번에 인턴 3차 프로젝트 주제로서 CDN파트의 Nagios와 Zabbix 모니터링시스템의 통합, 그리고 Zabbix의 고도화를 선택 했습니다. 제가 어제자 올린 업무보고에 링크를 올려놨습니다. 구축된 자빅스서버에 접속하실 수 있습니다. 아이디는 Admin, 비밀번호는 zabbix 입니다.


먼저 목차입니다. 크게 3가지 파트로 나뉘어져 있습니다. 먼저 자빅스 그자체의 업그레이드, 다음은 나기오스와 자빅스 플랫폼 통합에 따른 마이그레이션, 마지막으로 트러블슈팅과 향후 과제 순으로 발표 진행하겠습니다.

먼저 자빅스 업그레이드 입니다.

지금 사용하고계시는 자빅스 6.0버전은 동기식 수집 방식이여서 하나의 폴러가 데이터를 요청하고 받을 때까지 프로세스를 점유하고 있습니다. 이를 7.0버전에서는 이벤트 루프 기반 비동기 폴러로 변경되면서 하나의 프로세스당 1000개이상의 동시 검사를 지원하고, CPU 오버헤드를 감소시키며 데이터 수집 성능이 대폭 향상 되었습니다.
또 기존에 프록시는 하나밖에 사용하지 못해 단일장애지점 이었지만 프록시 그룹을 지원하게 되면서 프록시가 다운되더라도 다른 프록시로 작업이 전환되고, 그룹 내 프록시들에게 트래픽이 로드밸런싱되게 됩니다. 또 프록시에 메모리버퍼가 추가되어 수집 성능도 좋아졌습니다.

다음은 DB엔진 전환 입니다. 기존에 사용하고계시던 mySQL 8.0버전은 26년 4월부로 기술지원 종료 되었습니다. 또한 다음과같은 성능 향상을 위해 TimescaleDB플러그인을 연동한 PostgreSQL로 전환해야 합니다. 이는 시계열데이터 전용 압축 알고리즘을 이용해 디스크 용량을 90% 감축 시킵니다. 더해 데이터를 시간단위의 chunk로 관리함으로서 보관기간이 지난 데이터를 삭제할 때 Delete문 대신 Chunk단위로 Drop해버림으로 조회자체가가 줄어들어 DB부하가 0에 수렴하게 됩니다. 데이터를 시간단위의 청크로 관리하기 떄문에 시계열데이터의 쓰기 성능과 안정성도 향상됩니다.
다음은 기존에는 자빅스에이전트1을 쓰고계신걸로 알고있습니다. 에이전트2로 업그레이드하게되면 여러 엔터프라이즈 앱에 플러그인 템플릿이 지원됩니다. 뭐 따로 스크립트 더 만들 것 없이 PostgreSQL이나 레디스, HAproxy, Docker등을 간단하게 모니터링 할 수 있고 SSL인증서도 모니터링 할 수 있습니다. 또한 버퍼를 통한 데이터 유실방지를 지원하기 때문에 네트워크나 서버에 문제가 생겨도 수집데이터를 보관하고 있다가 정상화 되었을때 한번에 보내게 됩니다.

이런 장점들에 고가용성까지 더해서 완성한 Zabbix 서버 아키텍쳐 입니다. 총 6개의 노드로 구성되어있습니다. 각각 2개의 서버, 프록시, DB로 이루어져 있으며 인스턴스의 사양은 오른쪽에 보시는바와 같습니다. 이 아키텍쳐의 고가용성 전략에 대해 설명드리겠습니다.

먼저 DB계층 입니다. DB계층은 PostgreSQL 전용 고가용성 오픈소스인 Patroni를 이용했습니다. 패트로니는 DB노드들중 리더를 선출합니다. 그렇게 선출된 리더가 장애상황에 놓이게 되면 스탠바이DB를 리더로 승격시킵니다. 또 자체적으로 RESTAPI를 이용한 헬스체크를 지원합니다. /primary요청시 요청한 노드가 프라이머리라면 200을 응답, 아니라면 503을 응답합니다. 그리고 패트로니는는 ReaderDB가 아닌 DB들을 자동으로 ReaderDB화 동기화 시킵니다. 새로 생성되거나 재부팅시에 동기화 처리하고 둘다 떠있는 상태에서는 리더DB를 스트리밍 하게 합니다. 또한 패트로니가 PostgreSQL 프로세스의 소유권을 제어하며 관리하기 떄문에 설정이나 파라미터, 접근제어 규칙들을 전체 DB노드에 동기화 시킵니다.

이런식으로 패트로니가 고가용성을 유지하면서 리더디비를 선출하게 되도 아직 서버에서는 이를 알 수 가 없습니다. 그렇기 떄문에 HAproxy를 이용해서 아까 말씀드린 RESTAPI를 이용해 어떤 DB가 리더DB인지 알아내고 그 리더DB와 통신할 수 있도록 합니다.

다음은 서버와 프록시 계층입니다. 이 계층은 따로 고가용성을 위한 별도의 앱을 이용하지 않아도 zabbix자체적으로 이중화를 지원합니다. 자빅스는 여러 이벤트를 발생시키고 DB쓰기작업이 굉장히 많습니다. 그렇기에 중앙엔진을 하나로 유지하기 위해서 Active Active는 권장하지않고 자체적으로 Active Standby만 지원합니다. 그에 따라 DB에 주기적으로 노드의 상태를 업데이트하고 이를 바탕으로 Active와 Stanby를 선출합니다. Active노드가 다운되면 DB의 하트비트 갱신이 중단되고, 일정시간이 지나면 스탠바이 노드가 이를 감지하고 스스로 active로 승격하여 모니터링을 이어서 수행 합니다.

이렇게 만들어진 아키텍쳐를 여러방면에서 테스트 해보겠습니다. 먼저 부하테스트 입니다. 
자빅스서비스 규모의 단위는 NVPS, 초당 데이터 수집 건수 입니다. 목표를 좀 크게 잡아보았습니다. 자빅스 클라우드 페이지에서 모니터링할 기기를 1000대, 기기당 측정 항목 수 200개, 측정주기를 1분으로  설정하니 자빅스 가격계산기에서는 이와같이 엑스라지모델을 추천했습니다. 

엑스라지모델은 NVPS제한이 5000이었습니다. 그래서 5000NVPS를 만들어 보았습니다.

저는 부하테스트는 파이썬 멀티스레딩과 zabbix_sender를 이용해 진행했습니다. 인스턴스 4개에 더미 호스트 500개씩 총 2천개의 호스트를 띄우고 아이템25개, 트리거 25개, 수집주기 10초 짜리 더미테스트용 템플릿을 하나 만들었습니다. 그리고 이를 2000개의 호스트에 연결했습니다. 10초당 5만개의 데이터를 수집하기 때문에 NVPS를 5000으로 만들 수 있었습니다.

그렇게 부하테스트를 시작하자 메모리 크래시가 발생했습니다. 그러나 Proxy 설정 내 CacheSize=256M으로 상향 조정 후 재시작 하자 잘 작동하였습니다. 6시간정도 부하테스트를 진행하였는데 아쉽게도 DB 유틸라이제이션 60~80퍼센트 정도를 유지한것을 빼고는 문제가 발생하지 않았습니다. 실제 사용하게 되면서 NVPS가 커질 경우 DB노드의 사양을 지금은 4Core에 8GB 사용하는데 8Core에 32GB정로 확장해야 하겠습니다. 그리고 시간당 3GB정도의 로그가 발생했었습니다.

다음으로 이 부하테스트를 켜놓은 채로 장애조치 테스트를 시작했습니다. 장애조치의 경우 시스템로그만 찍어보고 DB에 저장된 로그를 찍어보지 못해 데이터 유실범위의 경우 정확하지 않을 수 있습니다.
먼저 리더DB의 VM을 일시중지 해보았습니다. 서버에서 로그를 찍어보았을 때 standbyDB가 리더로 승격되고 HAProxy에 200이 감지되기까지 14.6초정도 걸렸습니다 그후 자빅스 서버가 다시 DB와 연결되어서 완전복구 될 떄까지 18.6초정도 경과 되었습니다. 데이터손실의 경우 자빅스 서버는 DB에 flush하기 전에 HistoryCache에 보관하고, 그 시간도 1분이 안되어 캐시가 터지기 전에 복구 되었기 때문에 데이터 손실은 없었을 것으로 추정됩니다.

다음으로는 Active Server VM을 일시중지 해보았습니다. standby서버가 active로 승격되기까지 2.55초가 경과 되었고 프록시그룹과 연결되어 완전 복구되기까지 6.6초정도 경과 되었습니다. 데이터 손실의 경우 프록시 자체적으로 메모리버퍼를 보유하기 있기 떄문에 그쪽에서의 데이터 손실은 없었으나 종료 직전에 서버에서 받아서 DB로 Flush가지 까지의 1~3초정도의 데이터가 유실된것으로 추정됩니다. 

다음은 Proxy1 vm을 일시중지 해보았습니다. default 페일오버 기간이 1분이기 때문에 63초 뒤에 서버에서는 proxy1이 offline이라고 감지하게 됩니다. 그후 약 7초간 서버에서는 기존 proxy1이 모니터링하던 호스트들을 proxy2로 할당하고 proxy2에게 호스트들의 메타데이터 약 3MB를 전달해주게 됩니다. 그렇게 서비스가 완전복구 되는데 70.7초정도 걸리게 되고 그 이후 13초 정도 호스트에 심어져있던 에이전트의들의 메모리 버퍼에 있던 데이터가 들어오게 됩니다.
데이터의 경우헤는 호스트들에 있는 Agent가 직접 프록시로 데이터를 보내주는 Active수집의 경우에는 에이전트 자체의 메모리 버퍼링에 의해 공백이 생기지 않습니다. 하지만 프록시가 데이터를 수집해오는 패시브 수집데이터의 경우 프록시가 죽은 70초간 데이터 공백이 발생 되게 됩니다.
부하테스트 및 장애조치 테스트 결과 다양한 상황에서도 서버작동은 잘 되는것을 확인할 수 있었습니다.

다음으로 모니터링 플랫폼 통합 파트 입니다.
기존에는 모니터링 서버가 나기오스와 자빅스로 파편화 되어있어서 유지보수의 공수도 들고 일관된 가시성을 유지하기 힘들었다고 잘 모르지만 저는 그렇게 생각합니다. 어쩌면 기술부채의 한 종류라고 생각합니다. 나기오스랑 자빅스가 같은 호스트를 모니터링함에도 네이밍 컨벤션이 달라 통합하기도 힘들었을 것이라고 생각합니다. 그래서 전수조사 했습니다. IP를 기준으로 호스트네임과 대조하면서 중복호스트는 Zabbix 호스트에 통합시키고 Zabbix에는 없고 나기오스에서만 관측했던 20여개의 호스트를 자빅스 네이밍 컨벤션에 맞추어 추가했습니다.  

서비스의 경우 기존에 나기오스에서는 제가 확인하기로 아래와 같은 5종류의 모니터링하던것으로 파악됩니다. HTTP OK, SSL 인증서 체크, Pingcheck 이 세가지는 자빅스에서 치환되는 템플릿이 있어 편리하게 모니터링 할 수 있는 것을 확인하였고, 그 템플릿을 그대로 사용하거나 살짝만 커스텀 하면 되었습니다. 또한 언급해주셨던 도커 컨테이너 모니터링, 만료예정인 인증서 모니터링도 할 수 있었습니다. 하지만 자빅스에 존재하지않는 기능이 두개 있었습니다.

먼저 DNS체크 입니다. 기존 나기오스에서는 지정한 도메인을 각각 다른 DNS서버에 질의하여 응답 지연 시간 모니터링 하고 있었습니다. 이를 자빅스에서도 템플릿으로 만들어 편리하게 모니터링 하기위해 먼저

스크립트를 만들었습니다. 자빅스에서는 dns서버와 타켓 도메인, 경고를 보낼 시간초를 매크로로 입력받아 스크립드에 보내게 됩니다. 스크립트는 dig명령어를 이용해 dns상태를 점검합니다. 10초가 지나면 실패로 처리하게 됩니다. dig명령어로 나온 output을 파싱하여 자빅스로 보내주게 됩니다. 이렇게 만든 템플릿을 실제 호스트에 적용시켜 보았습니다. 결과값이 잘 나오는 것을 확인할 수 있었습니다.

다음은 RTMP_Check입니다. 이 RTMP 스트리밍 체크 같은 경우는 기존에 나기오스에서 호스트당 하나의 php파일로 관리하고 있었습니다. 다행이도 PHP 파일들이 IP주소를 제외하고 모두 동일해서 하나의 아이템화 할 수 있었습니다. 저는 자빅스에서 RTMP스트리밍 체크라는 아이템을 만들고 타입을 외부검사로 설정한 뒤 키값에 호스트의 IP주소를 들고가게 했습니다. 그리고 스크립트를 하나 만들었습니다. rtmpdump를 이용해서 키값으로 가져온 서버IP에 스트리밍 요청을 해 flv파일을 생성하게 했습니다. 성공하면 1, 실패하면 0을 반환하게 했습니다. 

그리고 이 아이템에 트리거를 추가해 하나의 템플릿으로 만들었습니다. 이 템플릿을 WZ01 서버에 적용하자 성공적으로 모니터링하며 1을 반환하는 모습입니다.
또 나기오스에 비해 자빅스는 오탐이 많다는 이슈를 말씀해 주셔서 오탐을 줄이기 위해 스크립트에는 1차 시도후 실패시 2초 후에 재시도를 하도록 하였고, 트리거에서도 이 스크립트의 실패가 2분이상 지속시 알람이 울리도록 설정했습니다. 이렇게 함으로서 기존 나기오스에서 모니터링하던것을 자빅스에서도 할 수 있도록 모두 템플릿화 하였습니다.

이 외에도 자빅스 6.0에 있던 커스텀 템플릿을 제가 정리하거나 바꾸기에는 문제가 있을것이라고 판단해서 그대로 7.0으로 가져왔습니다. 다만 사용하시던 커스텀 템플릿인 Linux템플릿의 경우 7.0에서는 호환되지 않는거나 충돌하는 아이템이 있고, 더해 상위호환 기본템플릿인 리눅스 바이 자빅스 에이전트가 있었습니다. 그렇기에 기존에 6.0 linux템플릿에는 있지만 7.0 linux by zabbix agent 템플릿에서는 없는 아이템들은 별도로 linux Custom Extention으로 빼놓았습니다. 윈도우도 마찬가지로 진행했습니다.

그래서 이런식으로 모두 마이그레이션이 완료 된다면 완료 후 한달까지는 동시가동 시켜서 오탐이나 문제들을 잡아 나가고 기존 vm을 백업서버로 만들어서 필요할 때 조회하게하고 1년 이후에는 폐기하거나 스냅샷으로 보관하는것을 제안 드립니다.

다음은 트러블슈팅 및 발전과제 입니다.
PostgreSQL을 패트로니로 묶어주면 오른쪽과 같이 레플리카, 리더로 나뉘어야 하는데 무슨짓을 해도 두 노드 모두 레플리카상태가 되어버리는 문제가 있었습니다. 로그들을 분석해보고 공식문서, patroni github, 커뮤니티등을 뒤져보니 postgreSQL이 여러 설정들을 하며 DB가 비어있는 상태가 아니였기 때문에 서로 리더로 올러서지 못하고 충돌하는 문제가 있었습니다. 그래서 PostgreSQL 서비스를 중단하고 모든 데이터 디렉터리를 제거 후 patroni를 재설치하니 문제를 해결할 수 있었습니다.

두번째는 Zabbix Proxy 연동 실패 문제 입니다. 프록시들이 설정을 어떻게 바꿔도 이중화된 서버와 통신이 안되어 데이터수집을 하지 않는 현상이 있었습니다. 알고보니 Zabbix는 데이터 수집방식이 Active냐 Passive냐에 따라서 설정파일에 IP주소를 적는 방식이 달랐습니다. 프록시나 에이전트 설정파일에 데이터를 보낼 이중화된 서버의 ip주소를 컴마를 통해 표기하면 둘 다 접속을 시도하고, 세미콜론을 통해 표기하면 세미콜론 앞에있는 IP에 먼저 접속 시도하고 안되면 두번째에 접속시도하는 매커니즘 이었습니다. 이를 조치하니 문제가 해결 되었습니다.

마지막으로 향후 발전 과제 입니다.
현재는 제 IXcloud 계정 권한 문제로 프로젝트를 2개 이상 만들 수 없습니다. 그렇기 떄문에 멀티 존을 구성할 수 없었습니다. 그 문제가 해결이 된다면 그림과 같이 멀티존 이중화 서버를 구축하고 싶습니다. 자세히 보시게되면 오른쪽에 DB가 3개입니다. (전환)현재는 ReaderDB 선출에 사용되는 etcd가 과반을 위해 총 3개의 노드가 필요한데 DB노드는 2개밖에 없기 떄문에 Server1 노드에도 etcd가 붙어있는 모습을 보실 수 있습니다. 이렇게 되면 Server1, DB1 노드가 죽게되면 DB2가 Reader로 올라올 수 없기 때문에 장애가 생기게 됩니다. 이를 방지하기 위해 굳이 데이터베이스 까지는 아니더라도 3번째 etcd를 AWS등에 멀티클라우드로 중재자로 둔다면 더 가용성을 확보할 수 있을것으로 기대됩니다.

또 오래 사용하시던 템플릿들, 호스트들 최신화 해서 모니터링 하는것도 과제로 볼 수 있을 것 같습니다.
